## 1. Problem, user, and focused goal

A shopping checkout can fail even when the component that first caused the failure is not the one reporting it to customers. For example, a slow or unavailable payment service may make checkout return an error, which the storefront then repeats. A new on-call developer sees several red signals and must decide where to inspect first. The semester project, AutoTriager, is a read-only investigation workbench for that decision. Its intended user is a junior on-call engineer who can inspect evidence and make the operational decision, rather than an agent that changes production systems. This user need remains a design hypothesis; no study with working on-call engineers has been completed.

Challenge 2 addresses one bounded question: **given one checkout incident, can the application identify a defensible first service to inspect, show records that support the suggestion, and abstain when those records are not enough?** The selected P1 task combines loading a bounded incident with running an existing-style analysis pipeline. A minimal evidence view completes the end-to-end feature. The input is a case with an incident interval, per-service telemetry, and provenance. The output is a ranked investigation candidate or an explicit insufficient-evidence decision, linked observations, missing information, and a place for human review. Success means the path can be executed on captured project data, its references resolve to original records, and both correct and incorrect diagnoses are measured. It does not mean autonomous root-cause proof or safe recovery action.

The original prototype replayed OpenRCA Bank cases. That provided a benchmark-shaped exercise, but it did not establish a concrete shopping-service need or show that the same telemetry existed in a runnable application. Instructor feedback challenged precisely those gaps: who would use the product, why they would need it instead of a prompt, and where its operational data would come from. The old Bank scores are therefore excluded from this project's results. The new experiment runs a controlled shopping workflow and collects its own records. This pivot makes the user story and the source of observations concrete, while creating a smaller and less realistic simulator than a production deployment.

## 2. Human Design and its provenance

My initial Human Design specified a read-only triage assistant for an on-call engineer, not a pull-request reviewer or automatic rollback controller. I decomposed the semester product into case loading, analysis, evidence presentation, historical review, interface integration, and later method improvement. For Challenge 2 I prioritized a single complete investigation path: load one selected system's case, run analysis, and show a candidate with inspectable evidence. Historical investigations, richer visualization, and method optimization were important follow-ons; supporting several unrelated systems was optional. This prioritization kept the first cycle within approximately two and a half weeks rather than making every product feature a prerequisite.

These constraints record my choices in the earlier project discussions. Those discussions themselves involved AI assistance; this section must not be read as a claim that an entirely AI-free, time-stamped design artifact existed before any AI contact. In this redesign, the human boundary decisions were specified before the implementation proposal was accepted.

The first design assumed public incident data and existing root-cause-analysis work would make the pipeline feasible. Its weak assumption was that a benchmark case automatically supplied a genuine user scenario. It also left unspecified how the project would produce new telemetry, whether a model could see answer labels, and how to compare the proposed workflow with a capable direct prompt. Those are design defects, not implementation details. I retained the human requirement - a bounded, evidence-backed, read-only decision aid - but changed the data source and acceptance test.

The revised human acceptance criteria are: (1) a real request passes through separately running shopping components; (2) the same request can be observed in normal, fault, and recovery phases; (3) the intervention label is kept outside the analyzer's input; (4) every displayed claim can be checked against a source record; (5) the operator can reject or defer the proposed diagnosis; and (6) an equally informed direct-model baseline is reported. The first three criteria establish a concrete experiment. The last three establish what a useful investigation aid would need to demonstrate.

## 4. Human-AI co-design decisions

| Design question | Human Design | AI proposal | Co-designed decision and reason |
|---|---|---|---|
| Real user and setting | Junior on-call investigator; evidence before action | General incident assistant using benchmark replay | One checkout incident in a runnable local shopping system; benchmark replay is excluded from current claims. |
| First task | Load a case and apply an existing analysis method | Broad pipeline and possible agents | One bounded normal/fault/recovery workflow plus a simple result view; no extra agent roles without a demonstrated failure. |
| Data | Metrics, traces, logs if available | Normalize data for model consumption | Preserve numeric values, timestamps, service names, trace/parent-span IDs, and raw file references; generate text only for compact model context. |
| Retrieval | Find the few relevant observations | Evidence-first selection | Rule-based top-48 observation selection with anomaly/error priority; call it evidence selection, not a trained or vector RAG system. |
| Grounding | Engineer must be able to verify a claim | Cite evidence IDs | Reject unknown IDs; resolve accepted citations to original records; distinguish a candidate investigation priority from proven causation. |
| Evaluation | Compare with correct labels | Weak direct-model baseline | Add a strong direct prompt, a clean control, private labels, and a named failure case. The corrected five-case comparison does not establish a method improvement. |

The co-design is stronger than the initial human sketch because the simulator, label separation, and source references are operationally specified. It is stronger than an AI-only proposal because the user need, comparison standard, provenance limits, and rejection of unsupported novelty claims are explicit human decisions. This is a design argument, not a measured user-study result.

## 5. Project data and processing

The evaluated data come from **this project's local four-process Python shopping simulation**, not the previously used OpenRCA Bank dataset and not an official Astronomy Shop run. The independently listening `frontend`, `checkout`, `catalog`, and `payment` processes exchange HTTP requests. A test order can be placed through the storefront. Controlled modes in the reported cohort are limited payment capacity under concurrent requests, a delayed payment response, catalog errors, checkout errors, and no fault. Each run has normal traffic, an intervention window, and recovery traffic. One example, `valid-capacity-001`, produced 24/24 successful baseline requests, 22/24 checkout failures during the capacity fault, and 24/24 successful recovery requests. Those counts are actual local HTTP results, not a model prediction.

The primary comparison uses **five newly generated `valid-*` case bundles: four fault runs and one clean control**. Their public `observations.json` files contain **534 observations: 260 spans, 234 logs, and 40 derived metric rows**. The approximately 1.02 MB total case-tree size includes raw data, private labels, and saved model outputs; it is not a standalone public dataset size. Span and log rows come from append-only local NDJSON files. Each observation carries a unique ID, service, UTC time, type, summary, source path and line where applicable, and trace/span IDs. Per-service error-fraction and p95-duration metrics are calculated in Python from span records in the alert and normal windows; they are **not independent Prometheus measurements**. Logs and spans can also describe the same failed request, so two signal types alone do not establish independent causal confirmation.

An earlier `local-*` development cohort is excluded from the primary comparison: its payment-delay intervention also changed the checkout-to-payment timeout, confounding the interpretation of a service-local delay. The corrected cohort holds that timeout constant across normal, fault, and recovery phases. Prior numbers from the development cohort should not be presented as valid evaluation evidence.

`incident.json` and `observations.json` are the public analysis inputs. The separate `ground_truth.json` records the injected mode, expected service, phase bounds, and observed HTTP status counts for the offline evaluator. The application loader rejects known answer-field names in public inputs and never opens the label file. A source-kind field distinguishes local simulation capture from official Shop capture and synthetic test fixtures. Preprocessing bounds observations by the incident interval, derives error-fraction features, keeps trace parent links, and validates raw references. The model sees at most 48 compact observations. An API call requires an explicit user confirmation that the demo case may be sent to Gemini.

The official [OpenTelemetry Astronomy Shop](https://github.com/open-telemetry/opentelemetry-demo) source is separately staged at release 3.1.0, commit `dedc0178918e260823323b8d95005a8cb924b007`, under its Apache-2.0 license. A capture adapter and an [experiment protocol](SIMULATION_PROTOCOL.md) target its Prometheus and Jaeger endpoints, including a controlled payment failure flag. **No official Shop run or captured official Shop case has been completed on this host.** The current evaluated dataset and screenshots must retain their `captured_local_sim` designation.

## 6. Methods, architecture, and evidence control

Python performs the bounded computations: request generation, timestamps, HTTP counts, error-fraction calculations, input validation, trace-parent bookkeeping, and source-link checks. The deterministic baseline counts only explicit anomalies and errors, caps repeated evidence within one modality, and adds a bounded preference for deeper failing child spans. Its score is a heuristic ranking of where to inspect, not a calibrated probability or a proof of root cause. It abstains if no qualifying signal exists, only one signal kind supports the leader, or leading scores tie. A payment request that times out before the payment worker writes an error record remains a known weakness of this signal strategy.

The LLM path uses Gemini (`gemini-3.5-flash-lite` in the saved measured runs). The primary comparison has two configurations: a strong direct prompt that asks the model to distinguish propagated errors, and a grounded configuration that prioritizes anomalous/error observations under the same 48-item cap. Both receive the public incident and compact observations; their evidence selection and instructions differ, so the comparison does not isolate retrieval by itself. A weaker direct prompt was used during discarded development runs and is not the primary comparator. The model returns a candidate or abstention, a short reason, evidence IDs, and missing evidence. A validator removes IDs not in the supplied set and requires two cited signal kinds before the grounded answer can be marked supported. The interface resolves each accepted ID to the full observation and raw source references. This is **metadata/rule-based retrieval plus LLM interpretation**, not embeddings or document RAG. Its separation of evidence extraction and reasoning is related to [EviRCA](https://arxiv.org/abs/2609.19825), but this project does not reproduce EviRCA's implementation or its published evaluation. Versioned runbooks may be added later only if a specific diagnosis failure requires them; intervention labels must never enter such an index.

The answer format is **candidate + evidence + provenance + uncertainty**. The UI marks the candidate as a starting point for investigation, allows the operator to inspect original records, and records an accept/reject/uncertain judgment with a written reason. It does not roll back code, change a feature flag, or present an unsupported answer as certain. Citation validity checks factual referential integrity, but cannot by themselves prove that a cited observation logically supports the model's conclusion.

## 7. End-to-end application feature

The local Streamlit application lets a user choose one captured case, see its symptom and provenance, run the deterministic baseline, optionally invoke Gemini, compare a small candidate list, inspect the associated observation table and raw records, and save a reasoned human review. The interface supports English and Chinese; this report is English for the course. The optional Gemini button requests confirmation before public demo telemetry is transmitted. The review form does not preselect a judgment: the user must explicitly choose accept, reject, or uncertain and enter a reason. A supported hypothesis also requires a selected candidate before an accept or reject review can be saved. A separate local storefront has a test-order button that actually makes the four-service request. The fault mode can be changed during a live demonstration, but the user-facing diagnosis remains read-only.

## 8. Measured results and failure analysis

The primary comparison is the corrected five-case `valid-*` cohort generated from this project's running local HTTP simulator. It is **measured local evidence, not an official Astronomy Shop result or a held-out estimate of production performance**. Each case has a known intervention in a private evaluator-only file. The same Gemini model processed the strong direct and grounded configurations. Fault localization means a supported answer named the injected service; clean abstention means no supported candidate for a no-fault case. Client-observed API latency is not engineer time saved or end-to-end incident resolution time.

| Method | Correct fault localization | Clean abstention | Wrong fault attribution | Clean false attribution | Valid cited ID sets / raw links | Median API latency |
|---|---:|---:|---:|---:|---:|---:|
| Strong direct prompt | **3/4** | **1/1** | 1/4 | 0/1 | 5/5 cases / 5/5 cases | 1,509 ms |
| Evidence-prioritized grounded prompt | **3/4** | **1/1** | 0/4 | 0/1 | 5/5 cases / 5/5 cases | 3,077 ms |

All five cases in each condition had a parseable model output and at least one cited observation; no API error was recorded in this cohort. Citation checks establish that IDs and raw links resolve, **not** that cited records are causally sufficient. The grounded condition was slower in this small sample; this is neither an accuracy gain nor a statistically supported latency conclusion.

| Case | Private intervention | Observed strong direct answer | Observed grounded answer | Interpretation |
|---|---|---|---|---|
| valid-capacity-001 | payment capacity | payment | payment | Both localized the intervention. |
| valid-catalog-001 | catalog error | catalog | catalog | Both localized the intervention. |
| valid-checkout-001 | checkout error | checkout | checkout | Both localized the intervention. |
| valid-clean-001 | none | abstain | abstain | Both correctly declined attribution. |
| valid-delay-001 | payment delay | checkout | abstain | Direct answer was a wrong fault attribution; grounded answer avoided that error but still failed to localize payment. |

The delay case isolates a difficult temporal pattern: payment takes longer than the **fixed** checkout-to-payment timeout, and checkout records an immediate dependency failure even though payment can later finish its own work. The strong direct prompt named checkout incorrectly. The grounded path abstained instead of inventing a supported payment claim, which is a narrower safety benefit, **not** a successful diagnosis. More complete timing and dependency checks may resolve this case, but that remains untested. The comparison also changes evidence selection, prompt wording, and the grounded output gate together. An ablation must vary these separately before attributing any behavior to retrieval itself.

An earlier development cohort is not included in these tables because its payment-delay intervention also changed the timeout parameter. That confound was corrected before generating `valid-*`; neither its case count nor its model scores are used as evaluation evidence here. The corrected set is still only five cases from one small simulator, and method decisions followed inspection of earlier development cases. It is therefore not a blind, independent benchmark.

## 9. Reproducibility and interpretation

The current source tree contains the four-process simulator, case schema and analyzer, Gemini client, Streamlit application, automated checks, capture adapter, an official-Shop protocol, and the measured `results/local_sim_valid.json`/`.csv` outputs. The case bundles with raw telemetry, private interventions, and model responses are local and ignored by Git. To reproduce the local path, install the Python dependencies listed in `requirements.txt`, run the controlled simulator to generate a fresh case, launch Streamlit, and inspect the evidence IDs against the raw NDJSON files. Gemini needs a separately configured API key and may be subject to account quota. The exact execution commands and environment prerequisites belong in the repository README and the final PDF appendix. A public GitHub URL must be inserted only after a repository has actually been created and verified; no URL is asserted in this draft.

The staged official Shop source is distinct from the locally executed simulator. The host's WSL prerequisites were enabled, but a restart and a working container runtime are still needed before any official-Shop capture can be claimed. The simulated topology, workload, and faults are deliberately small. Labels were defined by local injection, not by independent incident adjudication. No human user study has tested junior-engineer benefit, and no production data are included. Because the strong direct prompt ties the grounded path on fault localization, the current evidence supports an implemented **inspectable workflow**, not a claim of research superiority or a publishable algorithmic contribution.

## 10. Lessons and next development cycles

Human Design supplied the target decision and the rule that people, not the model, authorize operational action. AI assistance accelerated schema design, implementation, and test setup. Human review corrected the data/source mismatch, imposed a fairer baseline, rejected an unverified official-Shop claim, and required visible uncertainty. The central lesson is that a successful screenshot or citation validator is weaker evidence than a controlled comparison on a relevant setting.

Challenge 3 should test a harder **symptom-propagation problem** on a running, pinned official shopping demo: capture normal/fault/recovery metrics and traces, then ask whether the interface helps a reviewer distinguish an initiating service from its affected callers. The feature would add a trace-linked comparison of competing service hypotheses. Its evaluation would include predefined fault interventions, source-link checks, and a strong same-input direct-prompt comparator. This step depends on a verified container runtime and valid capture; if unavailable, it must be reported as incomplete rather than replaced with an upstream screenshot.

Challenge 4 should test **ambiguity and missing observations**, or multiple concurrent faults only if a simulator protocol can produce and label them reliably. The feature would expose competing explanations, request a targeted next check, and abstain when the visible telemetry cannot distinguish them. A more demanding evaluation would measure unsupported-attribution rate under removed or delayed signals and compare with the strong baseline. Challenge 5 would integrate the verified features, documentation, repeatable demonstration, and user feedback. These cycles align the course, a cautious research program, and a hackathon demonstration around one artifact. A paper would require held-out scenarios, stronger baselines, ablations, and independent user or system validation; a useful demo alone does not establish novelty.
